# 评测方法、指标口径与打假条件

> 这份文档的目的不是把结果说得更漂亮，而是把**结果的适用范围**说清楚。
> 一个不写适用范围的数字表，比没有数字更危险。

---

## 1. 评测要回答的问题

**「把客户需求变成一份可落地的技术方案」这件事，到底需要几个 agent？**

拆成两个可以分别验证的子问题：

| 子问题 | 怎么隔离出来 |
|---|---|
| 给它检索结果，值不值？ | A `no-evidence` → B `evidence-once` |
| 在检索之上再加编排与审校，值不值？ | B `evidence-once` → C `multi` |

**一次只改一个变量**，是这套设计能解释得清的唯一原因。三条流水线共享同一个 Intake ——「理解需求」不是本次实验的变量。

---

## 2. 三条流水线

| 名字 | 组成 | 模型调用次数（20 条用例实测均值） |
|---|---|---|
| `no-evidence` | Intake → 一次调用出方案（**不检索**） | 1.7 |
| `evidence-once` | Intake → 检索 1 次 → 一次调用出方案 | 1.7 |
| `multi` | Intake → 3 路并行取证 → 写作 → 独立审校（最多退回 2 次） | 4.5 |

三条流水线的产出**形状完全相同**（都是 `SolutionDraft` 契约），因此可以用同一套规则打分。

---

## 3. 指标定义

| 指标 | 定义 | 怎么算 | 已知缺陷 |
|---|---|---|---|
| **无依据断言率** | 找不到证据支撑的技术断言 / 总断言数 | 断言的 `evidence_ref` 不在本次运行的证据表里，或等于 `EV-NONE` | 是幻觉的**代理指标**。一条断言挂着真实来源，仍可能是对来源的误读 |
| **引用悬空数** | 引用了**不存在**的证据条数 | `evidence_ref` 有 `EV-` 前缀但查无此条 | —— 这一项单独统计，因为它比「老实说没证据」更严重：**它伪装成了有依据** |
| **约束覆盖率** | 有回应的客户约束 / 可判定的客户约束 | 按约束种类匹配关键词（见 §4） | 关键词代理，同义表达可能漏判；`kind=other` 的约束不计入分母 |
| **该追问时追问** | 欠规格用例中确实先追问的比例 | 用例标注 `needs_followup` × 产出里是否有 `followup_questions` | 见 §6「自证」 |
| **契约合规率** | 一次通过 schema 校验的环节 / 总环节 | 统计 trace 里 `contract_error` 事件 | 只反映「形状对不对」，不反映内容质量 |
| **单次成本** | 按公开单价换算的金额 | `prompt_tokens × 单价 + completion_tokens × 单价` | **不是账单**：未计缓存命中折扣、批量推理折扣、免费额度抵扣 |
| **平均调用次数 / tokens** | 结构开销的直接度量 | 由管线的实际调用累加 | token 在 mock 下是**估算值**（按字符折算），真实调用时以 API 返回的 `usage` 为准 |

**为什么必须同时看比率和绝对数**：比率可以被钻空子 —— 把断言删光，无依据断言率就变成 0。
所以报告里**必须同时给出断言总数**，并且有「断言数 ≥ 1」的契约约束兜底。

## 4. 约束覆盖率的关键词代理（最容易被质疑的一环）

关键词表：

```python
compliance   → 内网 / 私有化 / 合规 / 不出网 / 本地部署 / 数据安全 / 专属
latency      → 延迟 / 响应 / 时延 / 毫秒 / 秒内 / 实时
concurrency  → 并发 / qps / 吞吐 / 峰值 / 同时
cost         → 成本 / 费用 / 预算 / 单价 / 计费 / 元
quality      → 准确 / 效果 / 质量 / 命中 / 召回
```

**为什么用关键词而不是 LLM judge**：本实验要回答的是「多智能体值不值」。如果评分本身是个黑盒，
结论就不可复核。用规则打分，任何人都能拿 `results.csv` 自己重算一遍。

**代价**：模型用同义词（比如把「数据不出内网」写成「全链路本地闭环」）会被判成未覆盖。
这是**误判**，不是漏判方向上的保守 —— 它会让覆盖率偏低，对三条流水线同等偏低，因此不改变相对结论，
但**会低估绝对覆盖率**。

## 5. 故障注入：唯一能把功劳归因清楚的做法

**同一批坏输出，分别喂给有审校和没审校的流水线。**

如果只跑多智能体、看到它拦住了问题，那不能说明审校有用 —— 可能是检索起的作用。
只有对照组才能把功劳分开。

注入的三种故障分别考验不同的一层：

| 故障 | 种类 | 考验哪一层 | 预期 |
|---|---|---|---|
| `unsupported_claim` 伪造引用 | 偶发（只坏第一次） | Critic 的规则层 | 有审校的能拦住；没审校的直接发出去 |
| `constraint_ignored` 忽略约束 | 持续（一直坏） | 退改机制的上限 | 有审校的能发现，但**改不动** |
| `malformed_json` 非法 JSON | 偶发 | 契约层 + 本地重试 | 两条流水线都能吸收，**用不着编排** |

第三行是刻意加的：**不是所有故障都需要更复杂的架构。**
如果一个故障靠二十行重试代码就能吸收，为了它上一整套多智能体是不划算的。

## 6. 这份评测的四个已知缺陷（不许美化）

1. **mock 下的质量指标是自证的。**
   mock 判定「信息是否充足」的关键词与用例标注 `needs_followup` 用的是同一套规则，
   所以「该追问时追问 6/6」是构造出来的，不是测出来的。
   **同理，mock 下的无依据断言率反映的是脚本设定，不是模型行为。**
   要得到有解释力的质量数字，必须用真实模型重跑。

2. **用例只有 20 条，且是自建的。**
   不是行业基准，结论只在这个设定下成立。Anthropic 给的建议是「先拿约 20 条真实 query 立刻开评」，
   这条建议说的是**起步够用**，不是**够下结论**。

3. **约束覆盖率用关键词代理**（见 §4）。

4. **成本是估算**，且 mock 下为 0（没有单价）。

## 7. 打假条件：什么结果会推翻这套结论

如果一个项目只说自己对，那它不是实验。以下任一情况出现，本文结论即不成立：

| 条件 | 会推翻什么 |
|---|---|
| 用真实模型重跑后，`multi` 的无依据断言率**显著低于** `evidence-once`（正常路径） | 推翻「正常路径上编排不产生正确性」 |
| 把并行取证合并成一次检索 + 一次写作，质量指标不变而成本显著下降 | 推翻「多路并行取证有必要」这个前提本身 |
| `evidence-once` 在故障注入下也能拦住坏输出 | 推翻「审校的价值在故障路径」 |
| 把 `Critic` 的规则层换成纯模型判断后，拦截率不降而成本更低 | 推翻「规则层先行更划算」 |
| 关键词换成同义词后，覆盖率结论方向反转 | 推翻「覆盖率代理不改变相对结论」 |

**这些条件都写在仓库里，欢迎拿真实数据来打。**

## 8. 为什么不用 LLM-as-judge

不是因为它不好，而是因为**这次的问题不适合**：

- 位置偏好、长度偏好、分数不稳定 —— 已有的已知问题；
- 本实验的结论是「多花 3.1 倍 token 值不值」，**如果裁判本身也是个要花 token 的模型，账就更算不清了**；
- 规则化指标抓不到「方案写得切不切题、有没有说服力」这类软质量 —— 这一条如实承认，写进上面的缺陷表。

将来要补 LLM judge，正确的做法是**与规则指标并列报告**，而不是替换它。

## 9. 怎么复现

```bash
# 离线复现（零依赖、不花钱、结果确定）
python -m arksol eval --provider mock --out results/

# 真实模型重跑
export ARK_API_KEY=...
export ARK_MODEL=doubao-seed-2-1-turbo-260628
export ARK_PRICE_IN=3 ARK_PRICE_OUT=15
python -m arksol eval --provider openai-compat --out results/ark/
```

产物：
- `results/report.md` —— 报告（含适用边界）
- `results/results.csv` —— 逐条明细，可自己重算
- `results/raw.json` —— 原始记录
- `results/traces/*.jsonl` —— 每一步的输入、输出、token、耗时、校验结果
