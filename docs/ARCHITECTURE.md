## 0. 先回答三个必答题

任何 agent 项目都会被问这三个问题。先在这里答完，后面各节给依据。

| 问题 | 本项目的回答 | 依据 |
|---|---|---|
| **这个场景，模型直接聊能不能解决？** | **不能。** 单次对话可以让模型写出一篇读起来很专业的方案，但它**无法保证**方案里的技术断言有出处、无法保证客户说的约束都被回应、无法在信息不足时停下来追问。这三件事恰好是 ToB 售前最不能出错的地方。 | §1、§5 |
| **多智能体相比单 Agent 有实质收益吗？** | **有，但只在取证环节。** 撰写必须单线程；审校必须独立。把 agent 数量堆上去不会变好，反而更贵更不稳。**本仓库的核心工作就是用数字把这条边界画出来**，而不是假设它成立。 | §4、§6 |
| **每个选型能说清「为什么是它」吗？** | 逐条见 [`TRADEOFFS.md`](TRADEOFFS.md)，含**我否掉了什么、代价是什么**。 | 全文 |

## 1. 问题定义

### 谁在用

大模型平台（如火山方舟）的**产品解决方案 / 售前工程师**。日常工作是把客户的一句口语化诉求，变成一份能落到 PoC 的技术方案，并在客户没想清楚时把问题问清楚。

### 要解决的三个具体痛点

| 痛点 | 为什么致命 | 本项目的对应机制 |
|---|---|---|
| **方案会编** | 售前把「本模型支持 128k 上下文」发出去 = 拿公司信誉背书。这个数字错了，PoC 现场就翻车。 | 每条技术断言必须挂到一条**可追溯到来源**的证据上；Critic 逐条核对无依据断言 |
| **约束会漏** | 客户说了「数据不出内网」，方案通篇没提私有化 —— 这类漏项在 PoC 阶段才发现，返工代价极高 | 客户约束被抽成结构化字段，逐条检查是否被回应 |
| **欠规格时硬出方案** | 信息不全就编出一个方案，之后的补充信息推不翻它（早决策锁死） | Intake 发现关键信息缺失时，**直接输出追问清单，不出方案** |

### 明确不做的事（系统边界）

边界写清楚，比功能列表更能说明设计水平。

- ❌ **不做通用聊天助手。** 对话能力豆包自己就有，包一层没有增量。
- ❌ **不做无结构 swarm。** agent 互相自由协商的网状结构在工程上没有稳定产出，已有多方工程复盘把它列为干扰项。
- ❌ **不自动发方案给客户。** 所有产出都是**草稿**，必须有人过目 —— 涉及对外承诺的动作不该自动化。
- ❌ **不做知识库的自动爬取。** 知识库是人工维护的、每条标来源与读取日期；自动爬取会引入无法追溯的内容，正好毁掉这个项目存在的理由。
- ❌ **不追求超过单 Agent 的「综合评分」。** 目标是把**边界**找出来，得出「这个场景该用哪个」的判断，而不是证明多智能体更强。

## 2. 数据流与状态

```
客户原话
   │
   ├─► Intake ──────────► Requirement（结构化，过契约校验）
   │                        │
   │                        ├─ 若 critical 字段缺失 ──► 追问清单 ──► 结束（不出方案）
   │                        │
   │                        ▼
   ├─► Evidence ×N（并行，只读）──► EvidenceBundle（每条带 source_id）
   │
   ├─► Writer（单线程，唯一允许写入的环节）
   │       │  方案草稿：每条 claim 必须携带 evidence_ref
   │       ▼
   └─► Critic（独立）
           │  逐条核对 → 通过 / 退回（最多 2 轮）
           ▼
   方案草稿 + 证据表 + 追问清单 + 成本/延迟报告
```

**状态放在哪：外置，不放上下文。**

每个环节只拿到它需要的那一份，而不是把前面所有对话历史整个塞进去：

| 状态槽 | 内容 | 谁读 |
|---|---|---|
| `requirement` | 结构化需求、约束、未明确项 | Writer、Critic |
| `evidence` | 证据包，每条带 `source_id` / 原文片段 / 来源 URL | Writer、Critic |
| `claims` | 草稿里每条技术断言 + 它挂的证据 id | Critic |
| `attempts` | 已经试过什么、为什么被退回 | Critic、预算熔断 |
| `budget` | 已用 token / 步数 / 费用 | 编排器 |

**为什么外置**：任务态与执行历史如果共用同一份不断增长的上下文，早期判断会被带进后续决策，错误随步数累积而不是自愈。外置状态同时让「已经试过且失败」变成可查的指纹，避免无限重试同一动作。

## 3. 为什么是这四个角色

### Intake（需求理解）· 单线程

输入客户原话，输出结构化 `Requirement`：业务场景 / 能力诉求 / 硬约束（延迟、成本、数据合规、并发）/ 未明确的点。

**关键设计：欠规格时优先追问，而不是硬出方案。**
把完整指令拆成多轮边说边补，正确率会显著低于一次性给全 —— 因为模型会在早期轮次就假设前提、过早固化方案，之后很难推翻。所以本项目的默认行为是：**关键信息缺失 → 输出追问清单 → 结束**。这是产品判断，不是技术花活。

### Evidence（取证）· 可并行、多实例、严格只读

每个实例负责一摊（模型选型 / 限制与合规 / 成本与性能），各自检索知识库，产出**带来源的证据条目**。

**这是本项目唯一使用并行多智能体的地方**，理由是三条独立证据指向同一个结论：

1. 多智能体在**可高度并行、信息超出单窗口、需要对接大量工具**的任务上有明确收益；在强依赖、需共享上下文的任务上不划算。
2. 这类子任务最安全的形态是**只读**：它只贡献信息，不产生动作，因此不存在「两个 agent 各自做了互相矛盾的隐含决定」的问题。
3. 成本上，多智能体约是单 agent 的**十几倍** token。只把它用在真正需要并行的环节，是唯一能让账算平的做法。

### Writer（方案撰写）· 单线程

**全系统唯一允许「写入」的环节。**

并行的 agent 各自携带隐含决策（选这个模型还是那个、用哪种部署方式），如果让它们各自产出成品片段，最后拼起来会互相打架。工程结论是：**写入保持单线程**，其他 agent 只提供智能、不产生动作。

同时，Writer 的每一条技术断言都必须携带 `evidence_ref`。**不带引用的断言在契约层就不合法** —— 这是把「不许编」从提示词里的请求，变成代码里的约束。

### Critic（独立审校）· 独立于 Writer

检查两件事：

1. **有没有无依据断言** —— 逐条比对 `claims` 与 `evidence`，找不到支撑的标红
2. **客户约束有没有被回应** —— 拿 `requirement.constraints` 逐条打钩

**为什么必须独立**：让同一个上下文既生产又检查，等于没检查。Critic 拿到的是**结构化的产出物**（claims 数组），不是一段散文，这样才能做机械核对而不是凭感觉打分。

不合格 → 退回 Writer 重写，**最多 2 轮**，到线即停并如实标注「未通过审校」。

## 4. 可靠性机制（对应面试官的第二问）

「你的 agent 怎么做到稳定可靠」—— 这个问题不能靠形容词回答，只能靠机制。

| 机制 | 做什么 | 解决什么 |
|---|---|---|
| **契约校验** | 每个环节的输入输出都有 schema，不合格不许往下一步走，本地重试而非带病传递 | 多智能体最大一类失败是「规格问题」（200+ 条轨迹里占 41.77%），链条越长，模糊规格被反复解释、误差在交接处放大 |
| **外置状态** | 见 §2 | 上下文爆炸、历史错误累积 |
| **预算熔断** | token / 步数 / 费用三重上限 + 重复动作指纹；用掉 80% 仍未收敛即告警 | 失控循环与成本非线性增长（每步重发历史，累计输入随步数近似平方增长） |
| **全链路 trace** | 每个环节的输入、输出、耗时、token、校验结果写 JSONL | 出问题能定位到**具体哪一步**，而不是「它有时候就是不行」 |
| **故障注入测试** | mock 提供方可以故意产出非法 JSON / 超长输出 / 伪造引用，验证契约层与 Critic 能否拦住 | 不依赖真实模型也能回归测试可靠性 |

## 5. 对照实验设计

| 流水线 | 实现 | 想回答 |
|---|---|---|
| **A · single** | 一个 prompt 直接出方案 | 最省事的基线 |
| **B · single-guarded** | 强制结构化输出 + 让它自查一遍 | **便宜的改良能不能顶替多智能体** —— 这是最容易被忽略、也最可能成立的答案 |
| **C · multi** | 图里的完整流程 | 多花的钱买到了什么 |

指标（详细口径见 [`EVALUATION.md`](EVALUATION.md)）：

- **无依据断言率** = 找不到证据支撑的技术断言 / 总断言数 ← 核心指标
- **客户约束覆盖率** = 被回应的约束 / 客户明确提出的约束
- **契约合规率** = 一次通过 schema 校验的环节 / 总环节
- **追问命中率** = 该追问的用例里确实追问了的比例
- **单次成本（元）** = 按知识库里的官方单价换算
- **单次延迟（秒）**

**评测方法上的一个刻意选择**：不检查「它有没有走预设步骤」。多智能体即使起点相同也可能走完全不同的有效路径，按步骤打分会把有效路径判成失败。**评结果 + 评过程是否合理**，而不是评是否照剧本走。

## 6. 已知局限（不许美化）

写在最显眼的位置，因为这是这个项目唯一可信的地方。

1. **测试用例是自建的，约 20 条，样本量小。** 结论只在这个设定下成立，不是行业基准。
2. **知识库是演示用的，不是官方文档的替代品。** 每条都标了来源 URL 与读取日期，但**可能有错、可能过期**；接真实业务前必须重新核对。
3. **「无依据断言率」是幻觉的代理指标，不等于事实正确率。** 一条断言挂着一条真实来源，仍然可能是对来源的误读。
4. **成本是估算。** 按公开单价换算，未含缓存命中、批量推理折扣等实际优惠。
5. **只覆盖「需求 → 方案草稿」这一段。** 真实售前还有客户关系、竞争分析、报价审批、PoC 排期，这里一概不涉及。
6. **mock 模式下的数字不能当模型能力证据。** mock 是确定性脚本，用来验证**管线机制**（契约、熔断、重试、trace），不是用来测模型。
