# 选型取舍：我否掉了什么，代价是什么

> 一份只写「我用了 X」的选型说明没有信息量 —— 因为没人知道你放弃了什么。
> 这份文档逐条记录：**备选是什么 / 选了哪个 / 为什么 / 代价是什么**。

---

## 1. 用不用现成的 agent 框架（LangGraph / CrewAI / AutoGen / MetaGPT）

**决定：不用。核心管线只用 Python 标准库。**

| 备选 | 为什么没选 |
|---|---|
| LangGraph | 它解决的编排、状态机、checkpoint 问题，本项目都需要 —— 但**本项目要展示的正是「这些机制为什么必要」**。用框架会把机制藏起来，面试时讲不出细节。 |
| CrewAI | 默认迭代上限只限推理步数、不限单步内的工具重试，成本失控是已知失效形态。 |
| AutoGen | 官方已进入维护模式，新用户被引导到 Microsoft Agent Framework；把作品集建在这上面会显得信息过期。 |
| MetaGPT | 定位是软件公司模拟，与本场景不匹配。 |

**代价（诚实写出来）**：
- 自己写的编排器没有工业级健壮性，没有断点续跑、没有分布式、没有并发调度优化。
- 生态为零：不能直接复用框架的工具生态与可观测性集成。
- 行数更多，需要自己写测试。

**什么情况下我会改主意**：如果这个项目要长期维护、要多人协作、要接生产流量 —— 那就该用框架，而不是把有限的时间花在重造状态机上。**本项目的定位是可被读懂的样例，不是基础设施。**

---

## 2. 拆几个 agent

**决定：4 个角色，其中取证环节可并行多实例。**

**否掉的做法：顺序流水线角色（需求分析 agent → 方案 agent → 风险 agent → 报价 agent → 总结 agent）。**

这是最常见的拆法，也是我最先想到的拆法。否掉的两个理由：

1. **它把「步骤」当成了「角色」。** 一条顺序链条上每个环节都必须等前一个，没有并行收益，只是把一次调用拆成五次 —— 延迟和成本都涨，质量不涨。
2. **每一跳都是信息损失点。** 链条越长，交接越多次，模糊规格被反复解释，误差在交接处放大。

**代价**：
- 只有当任务真的能拆成互不依赖的只读取证子任务时，这个架构才成立。**如果场景变成强依赖的推理链，本项目这套拆法就不适用** —— 这也是实验要验证的边界，不是我能假设的。

---

## 3. 谁负责「写完」

**决定：只有 Writer 一个 agent 能产生成品内容，且是单线程。**

**否掉的做法：多个 agent 各写一段，最后拼接。**

并行的 agent 各自携带隐含决策（隐喻、风格、技术选型的细枝末节），各自产出片段再拼起来会互相打架。工程复盘里描述过这个现象：两个 subagent 并行做同一个东西，做出了风格完全不同的两个结果。

**代价**：
- 单线程写入是吞吐瓶颈，长方案不能靠并行加速。
- Writer 上下文压力更大，需要靠外部状态和证据包按需注入来控制。

---

## 4. 谁判定「做完了」

**决定：由外部的契约校验器与 Critic 判定，模型自己不参与完成判定。**

**否掉的做法：让 agent 自己说「任务已完成」。**

这是多智能体最隐蔽的一类失败：**日志里没有 error，轨迹看起来还在活动，但实际上在重复同一个失败动作**。把完成判定交给执行者本人，错误判定会被写回状态，成为后续决策的前提。

**代价**：
- 判定规则要人工维护（本项目的规则是：无依据断言率 = 0、全部客户约束被回应、schema 校验通过）。
- 规则覆盖不到的地方会误判 —— 比如方案「合规但不切题」，本项目目前不检测这一项，如实写在局限里。

---

## 5. 状态放上下文还是放外部

**决定：外置状态，按需注入。**

**否掉的做法：把前面所有历史都塞给下一个 agent。**

两个理由：

1. **成本**：无状态 API 每步重发全部历史，累计输入随步数近似平方增长。真实事故记录里有单会话 58 分钟 $72 的量级。
2. **正确性**：任务态与执行历史共用一份不断增长的上下文时，早期错误判断会被带进后续决策并累积，而不是自愈。

**代价**：
- 需要人工设计「哪个环节该看到什么」，写错了会漏信息。
- 调试时需要把外置状态打印出来对，比读一大段 prompt 麻烦。

---

## 6. 结构化输出怎么保证

**决定：每个环节都有 JSON schema 契约，不合格在本地重试，不带病传递。**

**否掉的做法：在提示词里写「请务必输出 JSON」，然后靠正则从散文里抠。**

**代价**：
- 严格校验会提高失败率（模型偶尔就是吐不出合法 JSON），需要重试次数与熔断配合，否则会变成成本黑洞。
- schema 一改，mock、测试、用例都要跟着改，维护成本真实存在。

---

## 7. 质量怎么打分

**决定：规则化指标（证据可溯源 / 约束覆盖 / 契约合规）+ 全量 trace 留档。**

**否掉（暂时）的做法：用一个 LLM-as-judge 打综合分。**

LLM judge 有几个已知问题：位置偏好、长度偏好、分数不稳定。而本项目想回答的是「多智能体值不值」，**如果评分本身是个黑盒，结论就不可复核**。

**代价**：
- 规则化指标覆盖面窄，抓不到「方案写得是否切题、是否有说服力」这类软质量。
- 规则本身可以被优化策略钻空子（比如把所有断言都删掉，无依据断言率就变成 0）—— 所以必须**同时看断言数量和覆盖率**，不能单看比率。这一点写进了评测口径。

---

## 8. 知识库从哪来

**决定：人工维护的小型知识库，每条标来源 URL + 读取日期 + 可信度，查不到就写「未查到」。**

**否掉的做法：自动爬取官方文档全站。**

**代价**：
- 覆盖窄，只能支撑演示规模。
- **必须有维护成本预算**：文档改版、模型下线、价格调整都会让它过期。这是这类工具真实的产品成本，也是为什么「知识库运营」本身是一个岗位。

---

## 9. 默认跑什么模型

**决定：默认 `mock`（确定性、零依赖、可注入故障）；可选任何 OpenAI 兼容端点。**

**否掉的做法：把仓库绑死在某个厂商上。**

**代价**：
- mock 模式的分数**不能当作模型能力证据**，只能验证管线机制。README 与结果表里必须把两者分开标注，否则就是误导。
- 需要额外维护一层 provider 抽象。
