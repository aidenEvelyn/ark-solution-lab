# 面试怎么讲这个项目

> 这份文档解决一个问题：**面试官问起来，你能不能接得住。**
> 里面的每个数字都来自仓库里的实测记录，被追问时可以顺着指回去。

---

## 一、三分钟讲述稿（背下来，别念）

面试官说「讲讲你这个项目」。你就按这四段说。

**第一段，说它解决什么（30 秒）**

> 我做的是一个售前方案助手。客户给大模型平台的第一句话通常很口语化：「我们想做个内部知识库问答，数据不能出内网，QPS 大概 50，预算每月两千」。售前要把这句话变成一份能拿出去谈的技术方案，这里面有两个容易出事的点：一是模型会编，方案里写「这个模型支持 128k 上下文」，错的就发出去了；二是客户约束会漏，说了数据不出内网，方案里没提私有化，等到 PoC 才发现要重做。

**第二段，说它怎么做的（60 秒）**

> 我把它拆成四个角色。第一个只做需求理解，并且要判断信息够不够出方案，不够就把问题列出来，不硬编方案。然后三路并行去知识库取证，只读、不写。第三个是写作，全流程只有它能写，而且每条技术断言必须挂一条证据，挂不出证据的断言在代码层面就不合法。最后一个是独立审校，检查引用完整性和客户约束有没有被回应，不合格打回去重写。
>
> 关键设计是**写入单线程**：并行取证的三个人心里各有各的小决定，让他们各写一段再拼，输出会互相打架。

**第三段，说结论（60 秒）**

> 我做了三条流水线跑同一批 20 条需求：不看知识库、检索一次、完整多智能体。
>
> 结论有点反直觉：**正常路径上，多智能体更贵但没有更好，3.1 倍 token、2.6 倍调用次数，质量指标一样。** 它值钱的地方在故障路径。我故意让写作环节使坏，同一批坏输出喂给两条流水线：伪造引用，有审校的 0/6 漏出去，没审校的 6/6 全漏。但**持续性的故障审校也救不了**，6/6 还是漏，这时候该停下来找人，不是让它再试一遍。
>
> 所以这个项目要回答的不是「多智能体强不强」，是「什么情况下它值这个钱」。

**第四段，说你怎么知道自己错了（30 秒）**

> 最有意思的是换成真模型之后挨的三次打。比如我原来把契约写在代码里，提示词里只用中文描述了一遍字段，真模型直接猜错字段名，重试三次全废，一次运行烧了 13 次调用。还有一回，模型老老实实标了「这条我没有证据」，我的审校却判它失败，两边卡死三轮。

> 这些都不是想出来的，是跑出来的。所以我在 trace 里强制记录模型的原始输出，没有这个，问题根本定位不到。

## 二、换岗位，重点不一样

### 面产品解决方案 / 售前岗

把重点放在**选型和取舍**上，代码细节一句带过。

要主动说的三句：

- 「我先想清楚了这个场景里该查的东西是稳定的三类，所以取证是固定的三路，不让模型自己决定拆几路。」
- 「我做过 trade-off：为什么不用现成的 agent 框架、为什么写入必须单线程、为什么审校要有规则层。这些写在仓库的 `docs/TRADEOFFS.md` 里，每条都写了代价。」
- 「结论我写成了『什么情况下值得上』，而不是『多智能体很强』。因为客户要的是判断，不是技术炫技。」

不要主动展开的：JSON Schema、线程锁、线程池保序。除非他问。

### 面技术 / 算法岗

把重点放在**工程细节**上。

主动说的四句：

- 「并行取证是真的多线程，所以预算计数器、trace 写入、mock 的调用计数全都加了锁。」
- 「契约校验用的是自己写的最小 schema 校验器，不引第三方库，因为核心管线我要保证 clone 下来零依赖就能跑。」
- 「预算是三重上限加动作指纹熔断。同一个查询反复重试会被熔断，这类失败在日志里没有 error，只会看到账单在涨。」
- 「退款规则我改过一次：只退回『能改而没改』的问题，承认没证据的不退。」

## 三、预判的追问与答法

### Q1 这个场景豆包直接聊能不能解决？

**答**：能写出一篇读起来很专业的方案，但保证不了三件事：方案里的技术数字有没有出处、客户说的约束有没有被逐条回应、信息不够的时候它会不会停下来问。这三件恰好是 ToB 售前最不能出错的地方。

**如果他说「加个 RAG 不就行了」**：对，我实验里也验证了这一点。**检索确实是主要解药**，给它证据之后无依据断言率从 100% 掉到 0，而且调用次数一次都没多。多智能体是在这之上再加的东西，它只在故障路径上起作用。这个结论我如实写在报告第一句。

### Q2 多 Agent 相比单 Agent 有实质收益吗？

**答**：在我这批任务上，正常路径没有。3.1 倍 token、2.6 倍调用，质量指标一模一样，我把这个写成结论的第一条。有收益的是故障路径：偶发故障能拦住，持续性故障拦不住。

**这道题是陷阱题，千万别硬吹。** 面试官想听的是你能不能说出边界。

### Q3 评测用例是你自己编的，那不是自证吗？

**答**：是，这一点我自己先标出来了。20 条用例是我写的，不是行业基准，换一批结论可能就变。而且用 mock 跑的时候更严重：mock 判定「信息是否充足」的关键词和我给用例打的标注是同一套，所以那一栏的 100% 命中是构造出来的，不是测出来的。

所以我做了两件事：一是在报告第一节就写明哪些数字有效、哪些没有；二是在 `docs/EVALUATION.md` 里写了五条打假条件，出现哪一条我的结论就不成立。

**这个答法会加分。** 面试官问这句，本来就是在看你会不会把话说满。

### Q4 无依据断言率怎么算的？关键词匹配靠谱吗？

**答**：分两步。第一步是引用完整性，断言的 `evidence_ref` 指向的证据 id 在不在本次运行的证据表里，这个是精确的。第二步是约束覆盖率，我用关键词做代理，`compliance` 这一类匹配「内网 / 私有化 / 合规 / 数据安全」这些词。

关键词有代价：模型用同义词会被判成没覆盖。它会让覆盖率偏低，但三条流水线同等偏低，所以不改变相对结论，只是绝对数被低估。这条我写进 `EVALUATION.md` 的已知缺陷里了。

**为什么不直接用 LLM 打分**：这次要回答的问题是「多花 3.1 倍 token 值不值」，如果裁判本身也是个要花 token 的模型，账就更算不清了。规则化打分别人能重算，这一点比打分更准更重要。

### Q5 成本怎么算的？准吗？

**答**：分两种。真实调用时用 API 返回的 `usage`，那是精确的。mock 模式没有 usage，按字符数折算，只能当数量级。

单价来自知识库，而知识库里的价格是公开文档的转述，可信度标的是「中」。所以最终金额是估算，不是账单，我没算缓存命中折扣和免费额度抵扣。这句话写在报告里。

**注意**：mock 那一轮的单价是空的，所以成本显示 0。代码里有一条明确的设计：**取不到单价就返回空，不猜一个数出来。**

### Q6 你怎么保证它不循环、不失控？

**答**：三道。

第一道是预算，token、费用、步数三个硬上限，用到 80% 就告警。
第二道是动作指纹，同一个「工具 + 参数」重复到次数上限就熔断，防的是那种日志里没 error、只在重复同一个无效动作的沉默失败。
第三道在流水线里：审校退回时，如果连续两轮是同一批问题，或者问题数没下降，就提前停止。

第三道是实测加上的。真模型下我发现，模型层审校每轮都能提出新的、也确实成立的意见，但那些意见多半源于客户信息不足而不是写作质量差，改到第几轮都收不了。

### Q7 如果模型一直改不好怎么办？

**答**：停下来，如实标注「审校连续 N 轮未通过」，把问题列出来交给人。

这一点我在故障注入里专门验证过：持续性的坏输出，审校 6/6 都能发现，但 6/6 都改不掉。**能发现问题不等于能解决问题**，这时候继续重试只是烧钱。

### Q8 你为什么不用 LangGraph 或者 CrewAI？

**答**：`docs/TRADEOFFS.md` 里第一条就是它。三个理由。

一是这个项目要展示的恰恰是「编排、状态机、checkpoint 为什么必要」，用框架会把这些机制藏起来，面试时讲不出细节。二是 CrewAI 的默认迭代上限只限推理步数、不限单步内的工具重试，成本失控是它已知的失效形态。三是 AutoGen 官方已经进了维护模式，把作品集建在上面会显得信息过期。

**代价我也写了**：自己写的编排器没有工业级健壮性，没有断点续跑、没有分布式。如果这个项目要长期维护、要接生产流量，那就该用框架，而不是把时间花在重造状态机上。

### Q9 为什么只有取证并行，写作不并行？

**答**：并行 agent 各自携带隐含决策。两个取证 agent 一个觉得选 A 档、一个觉得选 B 档，让它们各写一半再拼起来，输出自己会打架。所以并行的部分我给的是「只读取证」这种最安全的形态：只贡献信息，不产生动作。

写入这件事从头到尾一个人做。这是 Cognition 那篇《Don't Build Multi-Agents》里的结论，我验证过它在我这个场景成立。

### Q10 证据 id 为什么由管线分配，不让模型生成？

**答**：并行取证时三路 agent 各自从 EV-001 开始编号，必然撞车。而 id 撞车会让「这条断言挂的是哪条证据」这个判断失效。

原则很简单：**模型负责内容，不负责身份。** 不要相信模型生成的标识符。

### Q11 知识库里的数据你是怎么保证准确的？

**答**：保证不了，所以我换了做法：**每条都标来源 URL、读取日期、可信度**，还有一条完整性校验——引用一个没登记过的来源，加载直接失败。

数据本身主要来自方舟官方文档，但要说明一点：官方文档站是 JS 动态渲染的，抓取正文受限，所以有几个条目的可信度我标成了「中」甚至「低」，因为它们来自搜索引擎的渲染快照或者是二手报道。我在知识库的元信息里写明了「引用前请回原页核对」。

**这条其实是产品的真实成本**：知识库要人维护，模型下线、价格调整、文档改版都会让它过期。这也是为什么企业里会有专门的岗位干这件事。

### Q12 你说多智能体不划算，那这岗位还招它干嘛？

**答**：我说的是「它的收益只在特定条件下出现」，条件正好和岗位职责对得上。售前天天面对的是欠规格的需求和不能出错的对外承诺，这两个正好是多智能体能帮上忙的地方：欠规格可以靠追问环节挡住，出错的承诺可以靠独立审校挡住。

而且我验证的另一件事是**检索的价值远大于编排**。如果让我给一条落地建议，是先保证方案里的每条技术断言都能追溯到出处，再考虑要不要上多智能体。

### Q13 这个项目如果产品化，下一步做什么？

**答**：三件事，按优先级。

一是把知识库换成真实的、有维护流程的版本，并且加上过期提醒。现在这套东西的上限就是知识库的质量。

二是接客户的真实工单数据做评测。20 条自编用例只能证明机制通，证明不了效果。

三是把审校的意见分类。现在「缺信息导致的」和「写作质量导致的」混在一起，前者应该变成追问项而不是退回项，这样能省掉大量无用的重写轮次。

### Q14 为什么用 mock？那不是造假吗？

**答**：mock 是给两件事用的：CI 里的回归测试，和零成本复现管线机制。它不是用来测模型能力的，这句话在 README、报告第一节、代码注释里各写了一遍。

而且 mock 能注入故障，这是它最大的用处：我可以精确地造出「伪造引用」「忽略约束」「非法 JSON」三种坏输出，喂给不同的流水线看谁能拦住。这种事用真模型做不了，因为真模型不会乖乖地按我的要求出错。

### Q15 你最大的不足是什么？

**答**：评测。20 条自编用例、关键词代理的覆盖率、mock 下的质量指标自证，这三条加起来意味着**我能证明机制是通的，证明不了效果有多好**。

如果重做一遍，我会先找 20 条真实的历史工单，标好「客户约束有哪些」「正确答案该引用哪几条资料」，再来跑对照。现在的顺序反了，我先建了流水线再补评测。

### Q16 你从这件事里学到什么？

**答**：一句实在话：**契约必须同时出现在提示词里和校验器里。**

我原以为「契约不通过就重试」是个稳妥的设计，真跑起来才发现，如果模型根本不知道要什么形状，重试就是纯粹的浪费。同一份 schema，一边告诉模型要什么，一边检查它给了什么，这两件事必须同源。

## 四、五个别踩的坑

1. **别吹「多智能体更强」。** 你自己的数据说它在正常路径上没有更好。吹了就等于让对方翻你的报告打你脸。
2. **别把 100% 说成成果。** 那三条 100% 里有两条是构造出来的。
3. **别答「这个我还没想过」。** 上面十六个问题里至少有一半会被问到，答不上来比答错更伤。
4. **别只讲技术不讲业务。** 这是产品解决方案岗，讲清楚「为什么先保证可追溯、再考虑上多智能体」比讲线程池值钱。
5. **别说「我做了很多调研所以设计是对的」。** 调研只是输入。说你**验证了什么、推翻了什么**，尤其是你自己一开始判断错的那几次。

一行太长会被跳过，拆成两行：

```
Multi-Agent 售前方案助手（个人项目 · GitHub 开源）
· 用四个协作角色把客户口语化需求转成带证据的技术方案：并行只读取证 + 单线程写作 +
  独立审校（不合格退回），每条技术断言在契约层强制挂证据，无引用即不合法
· 设计了三条流水线的对照实验回答「该不该上多智能体」：正常路径多智能体贵 3.1 倍

  含故障注入测试、三重预算熔断、全链路 trace，257 个单元测试，核心管线零依赖
```
